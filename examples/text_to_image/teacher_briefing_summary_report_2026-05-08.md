# 面向课题汇报的阶段性总结报告

日期：2026-05-08

## 一、报告目的

本报告用于向相关老师汇报当前 `examples/text_to_image` 方向的研究进展、已发现的核心问题、问题产生的原因、代码与数据层面的依据，以及下一阶段建议的研究路线。

报告的核心问题是：

**为什么当前训练多次后，模型仍然无法稳定“根据输入条件生成正确物种图像”，以及后续应如何调整研究路线。**

本报告不是单纯的代码审查记录，而是对当前系统的整体研究状态做一次阶段性梳理，目的是：

1. 向老师说明当前失败不是简单的超参数问题，而是方法链路本身存在结构性问题。
2. 澄清当前实验系统中“蛋白条件”“文本条件”“物种条件”三者的真实关系。
3. 给出后续实验的可行路线，避免继续在当前不稳定方案上重复投入大量训练时间。

## 二、当前研究目标与系统现状

## 2.1 当前研究目标

从代码与数据组织方式来看，当前课题的核心目标可以概括为：

**利用鸟类相关蛋白信息，作为生成模型的条件输入，驱动模型生成与目标物种或相关形态特征一致的鸟类图像。**

更具体地说，当前希望实现的是：

- 输入蛋白相关条件；
- 扩散模型根据该条件生成图像；
- 生成结果能够体现不同物种之间的差异，最好还能反映部分与羽色、喙形、体型等相关的生物学特征。

## 2.2 当前系统的主要实现思路

根据 `examples/text_to_image` 下现有代码，当前系统采取的是如下路线：

1. 准备鸟类图像数据；
2. 从蛋白 embedding 或蛋白索引文件中，为每个物种构造一个蛋白 token 序列；
3. 使用一个自定义的 protein/species encoder，将这些蛋白 token 编码为若干 hidden states；
4. 直接用这个自定义 encoder 替换 Stable Diffusion 原本的 `CLIP text encoder`；
5. 用 LoRA 微调 UNet，使其在新的条件空间下生成图像。

换言之，当前系统实际上在做的是：

**Protein Encoder -> 直接替代 CLIP Text Encoder -> UNet LoRA 训练**

这条路线的优点是研究叙事非常直接：

- 不依赖自然语言；
- 条件来源纯粹来自蛋白；
- 从形式上实现了“蛋白直接驱动生成”。

但也正是这一步，带来了当前最核心的结构性问题。

## 三、当前已观察到的主要现象

结合代码检查和已有实验反馈，当前系统至少表现出以下现象：

1. 训练多次后，模型无法稳定根据输入生成正确物种图像。
2. 训练过程可能可以正常运行，loss 也可能下降，但生成结果对输入条件不敏感，或者只呈现出非常弱的物种差异。
3. 推理时如果输入不是严格的蛋白 token 串，而是自然语言或物种名，条件往往会失效。
4. 当前方法没有清晰地区分“图像生成质量问题”和“条件信息是否被模型真正使用”的问题。

这意味着：

- 当前系统并不是“完全训练不起来”；
- 而是更接近一种“可以运行，但条件控制机制本身没有建立起来”的状态。

这也是为什么继续单纯增加 epoch、调整学习率或多次重训，并不能根本解决问题。

## 四、核心问题总结

综合检查结果，当前主要问题可以概括为六类。

## 4.1 第一类问题：条件空间被整体替换，但没有完成语义对齐

这是当前最关键的问题。

Stable Diffusion 原本依赖的是：

- `CLIPTokenizer`
- `CLIPTextModel`

也就是说，扩散模型底层长期适应的是一种“文本语义条件空间”。

而当前代码直接将其替换成了：

- `ProtTokenizer`
- `speciesModel`

从张量接口上看，这样做是可行的，因为最终都能输出 `encoder_hidden_states`；
但从语义空间角度看，这种替换并不等价。

### 问题本质

当前自定义 protein encoder 输出的 hidden states：

- 形状上可能与 CLIP 输出兼容；
- 但其数值分布、token 结构、语义几何关系，并不天然与 Stable Diffusion 原有条件空间一致。

这意味着：

- UNet 虽然“收到了条件”，
- 但这些条件未必是它“会用的条件”。

更严重的是，当前训练时：

- protein encoder 基本被冻结；
- 主要更新的是 UNet LoRA。

这等于要求：

- 让一个原本适应 CLIP 条件空间的 UNet，
- 仅靠很小规模的 LoRA 调整，
- 去适应一个完全不同的蛋白条件空间。

这在工程和理论上都属于高难度设定。

### 直接影响

这会导致一种很典型的实验假象：

- loss 下降；
- 图像能生成；
- 但模型并没有真正学会“根据蛋白条件区分物种”。

也就是说，训练优化可能只是在学一些弱关联或数据偏置，而不是建立了稳定的条件控制机制。

## 4.2 第二类问题：当前输入协议与“文本 prompt”概念被混用，容易导致条件失效

当前训练脚本表面上仍在使用 `caption_column="text"` 这样的接口，README 中也保留了很多文本到图像的官方描述，但实际上：

- 当前 tokenizer 并不是自然语言 tokenizer；
- 它只是将输入字符串按逗号切分；
- 每个片段必须在蛋白词表中存在，才能被正确编码。

也就是说，当前系统虽然形式上仍叫 “text-to-image”，但它内部已经不是标准的“文本 prompt”语义，而是：

**protein token sequence-to-image**

### 具体表现

如果输入的是合法蛋白 token 串，例如：

- `tr|... , tr|... , [GRP] , tr|...`

则 tokenizer 可以正常处理；

但如果输入的是普通自然语言，如：

- `cute dragon creature`
- `a bird photo`
- 甚至单独的物种学名

这些内容在当前 protein tokenizer 下都不是合法 token，会退化成 `[UNK]` 或几乎无效的条件。

### 这意味着什么

这意味着当前系统里常见的两种行为其实是错误的：

1. 使用自然语言 `validation_prompt` 去判断训练效果；
2. 在推理时直接输入普通语言或物种名，期待模型按条件生成。

在当前设计下，这样的输入并不代表模型“不能理解物种”，而更可能代表：

**输入压根没有以模型真正可用的形式进入条件编码器。**

## 4.3 第三类问题：训练数据中的物种集合、条件编码器配置和 checkpoint 很可能不同步

通过检查配置文件和数据脚本，可以看到一个明显现象：

- 自定义 protein encoder 的默认配置仍然对应 `birds9`
- 而数据生成脚本已经在使用 `16birds`

这说明当前项目存在明显的版本漂移。

### 为什么这很重要

如果下面几项不是来自同一实验版本：

1. `species_classes`
2. `vocabulary`
3. `species_encoder_checkpoint`
4. 扩散训练实际使用的数据集物种集合

那么即使训练过程不报错，条件空间也可能已经失真。

### 可能的后果

- 某些物种没有被条件编码器正确建模；
- 某些物种对应的 token 分布与当前训练数据不匹配；
- encoder 输出的 species 表征并不稳定；
- 最终扩散模型看到的是一个“看似合法、实际上语义错位”的条件输入。

这类问题非常隐蔽，因为它常常不会直接报错，但会直接损伤条件学习效果。

## 4.4 第四类问题：数据构造方式天然鼓励模型忽略蛋白细节

当前数据生成方式的重要特点是：

- 对同一物种，会构造大量不同的蛋白子集；
- 这些蛋白子集再与该物种有限数量的图像重复配对。

这是一种典型的 many-to-one 条件映射。

### 问题本质

如果大量不同的蛋白条件最终都对应：

- 很相似的图像；
- 甚至相同图像的重复使用；

那么从优化角度看，模型最容易学到的策略是：

- 把所有这类条件近似看成同一种“物种模板”；
- 忽略其中更细粒度的差异信息。

### 这对当前研究的影响

如果课题目标只是“粗粒度物种分类式生成”，这类数据也许还能凑合；
但如果目标是“蛋白条件真正参与生成控制”，尤其是希望在不同蛋白组之间反映可见形态差异，这种数据构造方式会显著削弱可学信号。

换言之，当前数据设计在统计上更支持模型学会：

- “这是某种鸟”

而不支持模型学会：

- “为什么这一组蛋白条件会产生与另一组不同的形态倾向”

## 4.5 第五类问题：当前 protein encoder 更像分类器，而不是生成条件编码器

当前 `pretrained_encoder/` 路径下的实现，整体设计更接近一个：

- 物种分类 / 表征提取网络

而不是一个专门服务于扩散生成的条件编码器。

### 当前 encoder 的主要特点

- 输入是蛋白 token；
- 输出可以用于 species 分类；
- hidden states 是附带产物，而不是围绕生成任务设计出来的条件 token。

### 为什么这不够

生成任务所需要的条件编码器，不仅要：

- 区分不同物种；

还必须：

- 输出一组结构稳定的条件 token；
- 具备适合 cross-attention 使用的语义几何；
- 能把全局物种信息与局部 trait 信息分开表达；
- 支持 null-conditioning 和 guidance。

而分类器式 encoder 并不天然具备这些特征。

因此，当前并不是简单“encoder 不够强”，而是：

**encoder 的任务定义本身和扩散生成条件建模并不完全一致。**

## 4.6 第六类问题：当前评估方式不能回答“蛋白条件是否真的被用到了”

当前系统即使生成了一些看起来像鸟的图像，也不能据此证明模型真正使用了蛋白条件。

这是因为目前缺少系统性的评估协议来回答以下问题：

1. 不同条件输入是否会导致系统性输出差异？
2. 这些差异是否对应目标物种？
3. 这些差异是否不仅仅来自随机种子或数据偏置？
4. 在替换某一组蛋白条件时，图像是否在对应视觉维度上发生可解释变化？

### 当前评估的不足

如果仅依赖：

- loss 曲线
- 少量生成样图
- 主观“看起来像不像”

那么很难区分以下三种情况：

1. 模型真的学会了条件控制；
2. 模型只是学会了某种物种平均模板；
3. 模型主要在输出底模已有先验，与输入条件关联很弱。

这也是当前实验很难形成明确研究结论的重要原因之一。

## 五、关于“输入的蛋白信息中是否有一般文本”的澄清

这部分需要单独说明，因为这会影响老师对当前系统性质的理解。

经过检查，当前训练与推理中真正喂给模型的“蛋白条件”基本不包含一般自然语言文本。

它们主要由两部分组成：

1. UniProt 风格的蛋白 token，例如 `tr|...`
2. 特殊分隔符 `[GRP]`

### 这意味着什么

当前系统虽然沿用了官方 `text-to-image` 脚本外壳，但内部实际已经不是标准文本条件模型，而是一个：

**protein sequence conditioned diffusion model**

因此如果后续继续向老师汇报该系统，必须避免使用模糊表达，例如：

- “我们用了 text prompt”
- “模型理解文本描述”

更���确的表达应为：

- “我们当前使用的是蛋白 token 序列条件”
- “条件不是自然语言，而是结构化蛋白 token 输入”

这有助于避免老师误以为系统具备标准文生图模型那种 prompt 能力。

## 六、为什么当前失败不是简单超参数问题

在组会或汇报中，一个非常关键的判断是：

**当前问题不是“再多训练几次”就能自然解决的。**

原因如下。

## 6.1 不是学习率或 epoch 的首要问题

如果模型结构和条件建模是合理的，通常会观察到：

- 随着训练推进，条件敏感性逐渐增强；
- 不同物种 prompt 的输出开始可分；
- 验证样图逐步体现输入差异。

但当前系统的主要矛盾是：

- 条件本身未被稳定对齐到扩散模型原有条件空间；
- 数据又鼓励模型忽略细节；
- encoder 任务定义与生成任务并不一致。

在这种情况下，单纯调学习率或 epoch 更多是在放大已有系统误差，而不是修复其根因。

## 6.2 不是单纯 LoRA rank 不够

增加 LoRA rank 只能提高 UNet 适配能力，但不能解决：

- 输入条件空间本身与 CLIP 条件空间错位；
- tokenizer 协议与验证方式不一致；
- species set 配置不统一；
- 数据 many-to-one 噪声过高。

因此，继续把“训练不成功”主要归因于 rank 太小或训练步数不足，理论依据并不充分。

## 七、后续三条研究路线的定位

为了向老师清晰说明后续工作，不建议把所有方案混在一起，而应明确区分三条路线。

## 7.1 路线一：CLIP Only

目的：

- 用最标准、最稳定的文本条件路线，验证图像数据和训练流程本身是否可行。

意义：

- 它不是研究终点，而是 sanity check 和对照基线。

它可以回答：

- “如果只用物种文本 prompt，模型能否学会按物种生成？”

若答案是可以，则说明：

- 图像数据可学；
- 扩散训练流程大体正确；
- 当前主要问题更可能在蛋白条件接入方式。

## 7.2 路线二：Protein Only

目的：

- 完全去掉文本条件，检验蛋白是否能作为唯一条件驱动物种层级或 trait 层级生成。

意义：

- 研究叙事最纯粹；
- 但技术风险最高。

这条路线更适合作为研究实验分支，而不适合在当前阶段作为唯一主线。

## 7.3 路线三：CLIP + Protein

目的：

- 保留 CLIP 作为图像语义底座；
- 增加蛋白分支作为额外条件；
- 检验蛋白是否能带来超出文本基线的改进。

意义：

- 工程上最稳；
- 也是最有可能先产出可用结果的方向。

如果当前目标是：

- 尽快得到一个能用的蛋白条件生成系统；
- 同时又不放弃研究解释性；

那么这条路线最值得优先推进。

## 八、为何建议将当前蛋白输入结构化

当前蛋白输入虽然不含自然语言，但仍然存在一个重要问题：

- 它太“平”，缺乏明确角色结构。

建议后续把输入改成三层结构：

1. 全局物种 summary
2. trait / subsystem groups
3. 背景 proteome summary

### 原因

这样做有三个好处：

1. 能把与可见性状相关的蛋白组从背景噪声中分离出来；
2. 更容易形成可解释的条件 token；
3. 更容易做后续的 subsystem ablation 和 counterfactual 分析。

如果不做这一步，Protein Only 和 CLIP + Protein 两条路线后续都会受限。

## 九、推荐的研究推进顺序

面向课题推进，我建议向老师汇报时把后续工作拆成以下阶段。

## 第一阶段：先建立对照与 sanity check

目标：

- 做出 CLIP only 基线；
- 验证物种文本条件本身是否可学；
- 统一评估协议。

输出：

- 明确的 baseline 结果；
- ���定验证集和物种评估面板。

## 第二阶段：重构蛋白输入协议

目标：

- 从当前 flat protein prompt 转向 structured protein condition；
- 明确 global / trait / background 三类条件。

输出：

- 更适合生成任务的蛋白输入协议；
- 可供 Protein Only 和 CLIP + Protein 共用。

## 第三阶段：推进 CLIP + Protein

目标：

- 以较低风险验证蛋白条件是否能带来增益。

输出：

- 一个工程上可用、研究上可解释的双分支系统。

## 第四阶段：再推进 Protein Only

目标：

- 检验蛋白是否可以完全替代文本条件；
- 做更纯粹的研究实验。

输出：

- Protein Only 主实验与对照实验结果。

## 十、建议在汇报中重点强调的判断

如果需要向老师用较短时间讲清楚重点，建议突出以下五个判断。

### 判断 1

当前实验失败的核心，不是“训练不够久”，而是“蛋白条件空间与 Stable Diffusion 原有条件空间没有被正确对齐”。

### 判断 2

当前系统虽然沿用了 `text-to-image` 的脚本外壳，但实际输入不是自然语言，而是蛋白 token 序列，因此不能再用标准文本 prompt 的思维去理解它。

### 判断 3

当前数据构造方式大量复用同一物种图像配给不同蛋白子集，这会让模型倾向于忽略蛋白细节，只学习物种平均模板。

### 判断 4

当前 protein encoder 更像分类器，而不是生成条件编码器，因此它的 hidden states 不能自然等同于 CLIP text hidden states。

### 判断 5

后续更稳妥的路径不是继续在现方案上反复重训，而是分离出：

- CLIP only 基线；
- CLIP + Protein 主线；
- Protein Only 研究实验分支。

## 十一、现阶段可以形成的总体结论

综合目前代码、数据和实验现象，可以形成如下阶段性结论：

1. 当前系统已经证明：把蛋白 token 形式上接入扩散模型在工程接口上是可行的。
2. 但当前尚未证明：模型真正学会了根据蛋白条件稳定生成目标物种图像。
3. 当前失败的主要原因来自条件空间替换、输入协议混用、数据构造噪声、encoder 任务定义不匹配等结构性问题。
4. 因此，现阶段不建议继续将主要精力投入到“原方案多次重复训练”上。
5. 更合理的推进方式是：先建立 CLIP only 基线，再重构蛋白条件协议，随后推进 CLIP + Protein，并将 Protein Only 作为研究实验分支系统化设计。

## 十二、结语

如果向老师汇报当前工作状态，最重要的是传达一个清晰事实：

**我们并不是“模型还差一点超参数没调好”，而是已经识别出当前方案中存在方法级别的问题。**

这反而是一个积极信号，因为它意味着：

- 当前问题已经从“盲目尝试”进入“可分析、可拆解、可重构”的阶段；
- 后续工作不再是简单重复训练，而是可以围绕更明确的实验假设推进。

从研究价值上看，这一阶段最有意义的收获不是已有模型性能，而是已经明确识别出：

- 什么路径当前不稳；
- 问题为什么出现；
- 下一步哪些路线更可能产出可信结果。
